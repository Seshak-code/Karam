# GPU fronts vs CPU vs KLU — 2026-10-15 (Roadmap Phase 4; Apple M4 Pro, Metal via Dawn)

`klu_bench <matrix.mtx> <tree|klu> 3`, one process per run. `tree` was run twice:
- with the GPU path (the default): fronts of dimension >= 256 are eliminated in FP32 on the GPU until a pivot fails the threshold, then the CPU continues in FP64, followed by FP64 refinement;
- with `TREESPICE_GPU_FRONT=0`: CPU only.

fs = factor + solve per Newton iteration, in ms, the minimum of 3 runs. The matrices are the 8 SuiteSparse circuit matrices that finished in the 2026-10-13 baseline. The others (ASIC_100k, hcircuit, scircuit, dc1, trans4, G2_circuit, memplus, rajat15, circuit_4) do not finish in 300 s on either path.

## Reading

- **The GPU path is accurate and helps where large fronts factor cleanly:**
  - 2-7x on add20, meg4 and bcircuit;
  - 2.8x on the grid;
  - break-even where no front reaches 256.
- **It is 1.2-1.4x slower on circuit_2 and circuit_3:**
  - Most of their large fronts fail the threshold pivot within the first steps on the GPU. Measured on circuit_2: large fronts fail at steps 0, 1, 3, 6 and 159.
  - The rest of that front's dispatch chain still runs, as no-ops, before the CPU takes over.
  - Next GPU item: submit the steps in chunks and stop at the first failed one, or move the column search onto the GPU.
- **Letting the other threads factor on the CPU while the GPU is busy (`try_lock`) is not a win overall:**
  - meg4 gets 2x better (143 ms);
  - bcircuit gets 3x worse (1506 ms), because its big fronts then run on the slower CPU.
- **The GPU does not close the KLU gap.** With the GPU, TreeSPICE is still 48-2150x slower than KLU on the six matrices where it uses the GPU (3-6x on the two where neither path uses the GPU).
  - The cause is flops: the contraction tree does up to 20 000x KLU's flops, because BFS-level nested dissection on small-world circuit graphs builds huge dense separators.
  - That is an ordering problem, not an arithmetic one. A 2-7x faster dense kernel cannot make up four orders of magnitude in flops.
  - Closing the gap needs a fill-reducing ordering for non-grid graphs (approximate minimum degree, as KLU/AMD) feeding the same multifrontal tree. The GPU would then pay off only on the large fronts that remain.
